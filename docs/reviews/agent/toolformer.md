## 핵심 아이디어

Toolformer가 주목하는 것은 대형 언어 모델의 **역설적인 무능**이다. 몇 개의 예시만으로 새로운 태스크를 풀어내는 모델이, 정작 **두 자리 곱셈이나 사실 조회처럼 훨씬 작고 단순한 전용 모델이 완벽하게 해내는 일**에서는 자주 틀린다.

해법은 명확해 보인다. 계산기와 검색 엔진을 붙여주면 된다. 문제는 **어떻게 사용법을 가르칠 것인가**이다.

논문은 두 가지 조건을 내건다.

* **사람의 대량 주석 없이, 자기 지도(self-supervised) 방식으로 학습되어야 한다.** 주석 비용도 문제지만 더 근본적인 이유가 있다. **사람이 유용하다고 여기는 것과 모델이 실제로 유용하게 쓰는 것은 다를 수 있다.**
* **모델의 범용성을 잃지 않아야 한다.** 특정 태스크에 묶인 도구 사용이 아니라, **모델 스스로 언제 어떤 도구를 어떻게 쓸지 판단**할 수 있어야 한다.

Toolformer의 답은 **모델 자신을 심판으로 세우는 것**이다. 어떤 API 호출이 유용한지를 사람이 판정하는 대신, **그 호출이 뒤따르는 텍스트를 예측하는 데 도움이 되었는가**로 측정한다. 도움이 되면 남기고 아니면 버린다. 그렇게 걸러진 데이터로 모델을 finetuning한다.

결과적으로 GPT-J 기반의 **6.7B 모델이 여러 태스크에서 175B GPT-3와 대등**한 성능을 보였다. 도구 사용법을 배운 작은 모델이 그렇지 않은 거대 모델을 따라잡은 것이다.

## 방법론

### 전체 흐름

<!--Figure: Figure 2 (Key steps of the Toolformer approach)-->

일반 텍스트 데이터셋 $C$를 API 호출이 삽입된 데이터셋 $C^*$로 변환한 뒤, 그 데이터로 모델을 학습시킨다. 변환은 **세 단계**로 이뤄진다.

**1단계 — API 호출 샘플링**

각 API마다 few-shot 예시를 담은 프롬프트를 작성해, 모델이 텍스트에 API 호출을 삽입하도록 유도한다.

- 각 위치 $i$에서 모델이 **API 호출을 시작할 확률 $p_i$** 를 계산한다.
- 임계값 $\tau_s$를 넘는 위치 중 상위 $k$개를 남긴다.
- 남은 각 위치에서 최대 $m$개의 API 호출 후보를 샘플링한다.

API 호출은 `<API>`, `</API>`, `→` 특수 토큰으로 선형화되어 텍스트에 삽입된다.

**2단계 — API 호출 실행**

각 후보를 실제로 실행해 응답 $r$을 얻는다.

**3단계 — 필터링**

논문의 핵심이 여기에 있다. **API 호출이 유용한지를 손실 함수로 판정한다.**

호출 위치 이후의 토큰들에 대한 가중 cross-entropy 손실을 두 조건에서 비교한다.

- $L_i^+$ : API 호출**과 그 결과**를 문맥으로 주었을 때의 손실
- $L_i^-$ : API 호출이 아예 없을 때의 손실과, 호출은 있되 **결과가 없을 때**의 손실 중 **더 작은 쪽**

그리고 다음 조건을 만족할 때만 해당 호출을 남긴다.

$$
L_i^- - L_i^+ \geq \tau_f
$$

즉 **API 호출과 그 결과가 이후 텍스트의 예측을 실제로 개선했을 때만** 유용한 것으로 간주한다.

> **참고 — 왜 $L_i^-$에 "호출은 있되 결과가 없는" 경우를 포함하는가**: 이 설계가 정교한 지점이다. 만약 호출 없는 경우만 비교했다면, **호출을 삽입한다는 사실 자체가 주는 효과**(예컨대 관련 키워드가 문맥에 등장하는 것)와 **실제 실행 결과가 주는 효과**를 구분할 수 없다. 두 경우 중 더 나은 쪽을 기준으로 삼음으로써, **결과값이 기여한 몫만을 분리해 측정**한다. [Chain-of-Thought](../llm/chain-of-thought.md)가 점(`...`) 출력으로 "연산량만 늘리는" 대안 가설을 배제한 것과 같은 종류의 통제이다.

이렇게 만들어진 $C^*$로 **표준 언어 모델링 목적함수를 사용해 finetuning**한다. 중요한 점은 $C^*$가 **원본과 정확히 같은 텍스트**를 담고 있고 API 호출만 삽입되었다는 것이다. 따라서 모델은 같은 내용을 학습하면서, **자신의 피드백에 근거해 언제 어떻게 도구를 부를지**를 함께 배운다.

**추론 시**에는 평범하게 디코딩하다가 모델이 `→` 토큰을 생성하면 API를 호출하고, 응답을 삽입한 뒤 `</API>` 다음부터 디코딩을 이어간다.

<br/>

### 사용한 도구

도구 선정 기준은 두 가지이다. **입력과 출력이 모두 텍스트로 표현될 수 있을 것**, 그리고 **의도된 사용법의 예시를 몇 개 확보할 수 있을 것**.

- **Question Answering** — Natural Questions로 finetuning된 retrieval 기반 모델 Atlas
- **Calculator** — 사칙연산만 지원하며 결과를 소수점 둘째 자리로 반올림
- **Wikipedia Search** — Wikipedia 덤프에 대한 BM25 검색기
- **Machine Translation** — NLLB(600M) 다국어 번역 모델. 원문 언어는 fastText로 판별
- **Calendar** — 현재 날짜를 반환하며 입력을 받지 않음

기반 모델은 **GPT-J(6.7B)** 이고, 데이터는 CCNet의 부분집합을 사용한다.

## 실험 결과

### 태스크별 성능

<!--Figure: Table (Results on downstream tasks)-->

- **LAMA(사실 완성)**: Toolformer가 베이스라인은 물론 **GPT-3와 OPT-66B까지 앞섰다.** 주로 QA 도구를 사용했다.
- **수학(ASDiv, SVAMP, MAWPS)**: 계산기를 붙인 Toolformer가 베이스라인 대비 **성능을 대략 두 배로** 끌어올렸고, OPT-66B와 GPT-3를 능가했다. 계산기가 **약 97%의 경우에 사용**되었다.
- **QA(Web Questions, Natural Questions, TriviaQA)**: 같은 크기의 베이스라인은 앞섰지만 **GPT-3에는 미치지 못했다.** 논문은 원인을 명확히 짚는데, **모델이 검색 엔진과 상호작용할 수 없기 때문**이다. 질의를 다시 작성하거나 여러 결과를 훑어볼 수 없어, 한 번의 검색이 실패하면 그대로 끝난다.
- **다국어 QA(MLQA)**: 대부분의 언어에서 베이스라인을 개선했으나 GPT-3를 일관되게 앞서지는 못했다.
- **시간 관련(TempLAMA, Dateset)**: 캘린더가 도움이 되었지만, TempLAMA에서는 **기대만큼 자주 캘린더를 사용하지 않았다.**

<br/>

### 범용성이 보존되는가

논문이 중요하게 확인한 것은 **finetuning이 언어 모델 자체를 망가뜨리지 않았는가**이다.

API 호출을 비활성화한 상태에서 WikiText와 CCNet 부분집합에 대한 perplexity를 측정한 결과, **원본 모델과 거의 차이가 없었다.** $C^*$가 원본과 동일한 텍스트를 담고 있다는 설계가 여기서 효과를 발휘한다. 도구 사용 능력을 얻으면서 기존 능력을 잃지 않았다.

<br/>

### 도구 사용도 emergent ability이다

GPT-2 계열(124M, 355M, 775M, 1.6B)과 GPT-J로 규모별 실험을 수행했다.

**약 775M 파라미터 부근에서야 도구 활용 능력이 나타난다.** 그보다 작은 모델은 도구를 주든 안 주든 성능이 비슷했다. 도구를 호출하는 형식은 흉내낼 수 있어도, **그 결과를 실제로 활용하지 못하는 것**이다.

또한 모델이 커져도 **도구를 쓸 때와 안 쓸 때의 격차가 줄지 않고 유지**되었다. 규모가 커지면 도구가 필요 없어지는 것이 아니라, **계속 유용하다**는 뜻이다.

<br/>

## 한계점

논문이 직접 열거하는 한계들이다.

- **도구를 연결해서 쓰지 못한다**: 한 도구의 출력을 다른 도구의 입력으로 넘기는 **연쇄 사용이 불가능**하다. 각 도구의 API 호출이 **서로 독립적으로 생성**되었고, finetuning 데이터에 연쇄 사용 예시가 전혀 없기 때문이다.
- **상호작용적으로 사용하지 못한다**: 특히 검색 엔진에서 치명적이다. 수백 개의 결과를 훑어보거나 질의를 다듬어 다시 검색하는 것이 불가능하다. QA 성능이 GPT-3에 못 미친 직접적 원인이다.
- **입력 표현에 민감하다**: API를 호출할지 말지 판단할 때 **입력의 정확한 표현에 좌우된다.** 언어 모델이 프롬프트 문구에 민감하다는 알려진 특성이 그대로 나타난다.
- **샘플 효율이 매우 낮다**: 100만 개가 넘는 문서를 처리해도 유용한 계산기 호출 예시는 **수천 개 수준**만 얻어진다. 대부분의 후보가 필터링에서 탈락하기 때문이다.
- **도구 사용 비용을 고려하지 않는다**: API 호출에 드는 연산 비용이 판단에 전혀 반영되지 않는다. 굳이 부르지 않아도 될 때 부르는 것을 막을 장치가 없다.

여기에 구조에서 따라오는 제약도 짚어둘 만하다.

- **유용성의 기준이 다음 토큰 예측**이라는 점은 우아하지만 완전하지 않다. **텍스트 예측에 도움이 되는 것과 태스크의 정답을 맞히는 것이 항상 일치하지는 않는다.**
- 다섯 개의 고정된 도구, 그것도 **모두 텍스트 입출력**으로 한정된다. 상태를 갖는 도구나 복잡한 인터페이스는 다룰 수 없다.

## 인사이트

- **무엇이 유용한지는 모델이 판단하게 한다**: 이 논문의 철학적 핵심이다. 사람이 "여기서 계산기를 써야 한다"고 주석하는 대신, **모델이 자신의 손실 감소로 유용성을 스스로 측정**한다. 사람의 직관과 모델에게 실제로 도움이 되는 것이 다를 수 있다는 문제의식은, 합성 데이터를 다루는 여러 연구가 공유하는 관점이다. [BLIP](../vlm/blip.md)의 CapFilt가 모델로 데이터를 생성하고 모델로 걸러낸 것과 같은 **model-in-the-loop 패턴**이다.
- **주관적 판단을 측정 가능한 양으로 바꾸기**: "이 도구 호출이 유용한가"는 원래 주관적 질문이다. Toolformer는 이를 **손실 감소량**이라는 스칼라로 환원했고, 덕분에 자동화가 가능해졌다. 다만 그 대가로 **유용성의 정의가 다음 토큰 예측으로 축소**되었다는 점도 함께 봐야 한다.
- **도구 사용을 배우는 두 갈래**: [ReAct](react.md)는 사람이 쓴 궤적을 프롬프트에 넣어 **추론과 행동을 교차**시켰다. Toolformer는 도구 사용을 **가중치에 새겨 넣어** 추론 시 별도의 프롬프팅 없이 동작하게 했다. 같은 질문에 대한 서로 다른 답이며, **오늘날의 function calling 모델은 Toolformer처럼 학습으로 내재화하되 ReAct식 루프로 운용**하는 절충에 가깝다.
- **두 논문의 한계가 서로를 가리킨다**: Toolformer가 인정한 연쇄 사용과 상호작용의 부재는, 정확히 ReAct의 반복 루프가 해결하는 지점이다. 반대로 ReAct의 프롬프트 의존성과 컨텍스트 제약은 Toolformer의 학습 방식이 해결하는 지점이다. **두 접근이 상보적**임을 각자의 한계가 드러낸다.
- **emergent ability의 문턱은 능력마다 다르다**: 도구 활용은 약 775M에서 발현되는데, CoT식 추론이 100B 규모를 요구했던 것과 대비된다. **"도구를 부르고 그 결과를 반영하는" 능력이 "여러 단계를 스스로 추론하는" 능력보다 훨씬 이른 시점에 나타난다**는 것은, 두 능력의 난이도가 질적으로 다름을 시사한다. 작은 모델에서 도구가 특히 유효한 전략일 수 있다는 실용적 함의도 있다.
- **기존 능력을 지키는 것이 설계 조건**: $C^*$를 원본과 동일한 텍스트로 유지해 perplexity가 보존되도록 한 것은, Flamingo의 tanh 게이팅이나 Qwen2.5-VL의 하위 호환 설계와 같은 계열의 사고이다. **새 능력을 얹을 때 기존 능력을 훼손하지 않는 것이 먼저**라는 원칙이 여기서도 반복된다.
- **규모가 커져도 도구는 필요하다**: 모델이 커져도 도구 사용의 이득이 줄지 않았다는 관찰은, 도구를 "작은 모델의 보완재"가 아니라 **영구적인 구성 요소**로 봐야 함을 시사한다. 계산과 최신 정보 조회는 파라미터에 욱여넣기보다 외부에 맡기는 편이 근본적으로 낫다는 뜻이기도 하다.
